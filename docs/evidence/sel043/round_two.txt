Smallest set known to reproduce: q4, files 27-35 (test_desk002_registration_event_lines.py through
test_disp003_governing_header.py), red once in two runs. No half of it and no single file of it reproduced. Read

in which Neo4j's scan returns same-named nodes, which depends on the store's id allocation and reuse history, not on
any one earlier test.

Cause
-----
tests/dispatch_scaffold.py: every dispatcher scenario writes ResearchTask nodes into the session's one shared test
database (neo4j_driver is session-scoped; these tests take no clean_test_db), and they all use the same few names
(a, b, ...) with one created_at, 2026-10-17T00:00:00Z. Nothing removed an earlier test's `a`. So:
  - task_states() ({t.name: t.state}) returned the state of whichever `a` the scan returned last, and
  - the dispatcher's own queue (seldon/commands/dispatch.py _tasks, ORDER BY t.created_at, a tie for every `a`) could
    launch an earlier test's still-proposed `a`, whose file exists in every scratch project as cc_tasks/a.md.
Each red test read the state another test expects ('completed' where 'blocked' and the reverse), which is the
desktop session's observation in the addendum, confirmed: the second `a` was an earlier test's node.

Whether this is this branch's: the cause is in code this branch did not touch (register() and task_states() are
unchanged by it; its scaffold change is the snapshot_lease option). The branch changed which order the scan returns
(its conftest change, the R9 shim on the session, and its added tests change the database's history), and main's
tree passed the q4 set in its one control run; which of the branch's changes moved the order is not established and
was not pursued, because the order was never something these tests could rely on.

Fix (5 lines, under the addendum's twenty)
------------------------------------------
tests/dispatch_scaffold.py register(): before creating the scenario's task, MATCH (t:ResearchTask {name: $n})
DETACH DELETE t. A scenario's task name is its own. No assertion of either test changed; nothing was deselected or
skipped; gate_command is unchanged. A scan of tests/ (AST: one test function registering the same literal name twice)
found no test that registers one name twice, so no test depended on two same-named tasks.

Test that catches it, written first and red before the fix:
tests/test_sel043_scaffold_task_names.py::test_registering_a_name_an_earlier_scenario_left_in_the_graph_leaves_only_
this_scenarios_task: an earlier scenario's `a` set to completed, then this scenario's `a` registered; asserts one `a`
and that it is this scenario's. Before the fix: 1 failed. After: 1 passed.
