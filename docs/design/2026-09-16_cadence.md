# `dispatch.cadence` — a schedule that produces a task

**Date:** 2026-09-16. Seldon-side record of the cadence half of the standing dispatcher, built
for `ai-readiness-kg` and usable by any project that opts in. The design note is that project's
`docs/design/2026-09-15_DN-006_standing_dispatcher.md`; **decision 8** is the spec, and its
`ADDENDUM_02` records the five places this build found the note incomplete. The command group
itself is `docs/design/2026-09-15_standing_dispatcher.md` here.

## The condition

The dispatcher closed dispatch latency for tasks that already exist. It did nothing for work
that is due on a calendar: a monthly measurement cycle (DD-060 in that project) still needed a
person to notice the month had turned and write the task. A cycle whose date is set by human
attention is a cycle whose date is not the calendar's, and for a dated measurement that is the
one property that may not drift.

## The decision, restated

**A schedule produces a task file. It does not run anything.**

When a period is due and no instance for it exists, the pass renders a template, registers the
rendered file through `seldon cc register`'s own code path, commits it, and stops. The task then
flows through the ordinary criteria — candidacy on the three headers, c1 to c9, the claim, the
launch — like a task a person wrote. There is no second evaluator, no second claim, no second
log, and no path by which a schedule can start work the criteria would have refused.

The alternative — a scheduler that ran the cycle directly — would need its own copy of every
guard, and the copies would drift. This way the cadence adds exactly one capability to the
system: a file appearing on a calendar.

## Shape

```yaml
dispatch:
  cadence:
    - name: scan_cycle                       # keys the instance file and the event
      rule:
        monthly_first_weekday: monday        # the closed vocabulary; see below
        at_utc: "00:00"                      # quoted: YAML reads 00:00 as sexagesimal
      template: cc_tasks/templates/scan_cycle.md
      instances_dir: cc_tasks
      cycle_name_format: "scan_{date}"       # the project's naming convention, not Seldon's
      start_period: "2026-10"                # the first period this schedule may serve
      last_instance: ""                      # written back for a reader; NOT the guard
```

`seldon/core/cadence.py` is the calendar, the instance check, the render and the write-back —
all pure or filesystem-local, so the arithmetic is testable against a hand-checked table rather
than against a reimplementation of itself. `seldon/commands/dispatch.py` holds the pass
integration: the gate on creating anything, the registration, the event and the commit.

## The rule vocabulary is closed, and short on purpose

`monthly_first_weekday` is the only rule type implemented, because it is the only one any
project has asked for. **A second rule type is a code change with a test**, not a string
somebody types into a config file. An open-ended cron expression in a YAML key is an
interpreter nobody wrote, and its failure mode is the worst one available here: a schedule that
silently never fires looks exactly like a quiet month.

For the same reason an unreadable rule **refuses at config load**, not when it fires. A rule
that failed at 00:00 on the first Monday would fail unattended, at the only moment it mattered,
and nothing would be watching.

## `catchup=False`, by construction

Due-ness is evaluated against the **current period only**. A dispatcher that was off for two
months creates this month's instance and back-fills nothing. A back-filled cycle would measure
today's hosts under last month's name, which for a dated measurement is worse than a gap: a gap
is visible and a mislabelled measurement is not. Airflow's `catchup` flag exists because every
scheduler has to answer this question; this one answers it the same way and says so.

## `start_period`, and the condition `catchup=False` does not cover

`catchup=False` stops the cadence back-filling **earlier** periods. It does nothing about the
period a schedule is switched on *inside*.

The first project to install this hit exactly that. The monthly cycle was enabled on
2026-09-16; September's first Monday was the 7th; September had already been measured by a
hand-dispatched cycle nine days earlier. The rule said due, the instance glob found no *cadence
instance* on disk — correctly, there was none — and the first clean-tree pass would have created
a second measurement of a month that already had one.

So every entry declares `start_period`, the first period it may serve, and it is **required**
rather than defaulted. The obvious default — "the period the config was written in" — would
depend on a file's mtime, and a schedule whose start nobody can read off the config is a
schedule nobody can check. Prior art is Airflow's `start_date`, which exists for this condition
and for no other.

`status` and `seldon go` report it as a value (`not due (before start_period 2026-10)`) rather
than as silence, because "not due" and "not yet in scope" are different facts and an operator
watching a schedule that never fires needs to know which one they are looking at.

## The guard is the file, never the config field

`existing_instance` globs `<instances_dir>/*_<name>_<period>.md`. The date prefix is free, so a
dispatcher that was down on the 5th and fired on the 19th finds the instance it would have
created and creates nothing.

`last_instance` is written back into `seldon.yaml` for a reader, and if that write fails the
pass says so on the event and carries on — because the file is the guard. Were the config field
the guard, a hand-edited line or a half-completed write would produce two task files for one
period: two measurements of the same month under two names.

The write-back is a **surgical edit of one line**, not a `yaml.safe_dump` round-trip. Every key
in a real `dispatch:` block carries the comment that says what its value is based on; a
reserialisation would delete all of it, and the dispatcher must not be the thing that strips a
config file of its reasons.

## The dispatcher commits, and here is why

DN-006 decision 8 says the rendered task "flows through decisions 2 to 5 like any other task".
Decision 2's **c1 requires the task file to be git-tracked** and **c7 requires a clean working
tree**. A rendered file that is never committed fails both — forever, for every task in the
queue — so the cadence would create the cycle and then wedge the dispatcher until a person came
and committed it. That is the exact latency the mechanism exists to remove. **The commit is
entailed by decision 8, not added to it**, and DN-006 ADDENDUM_02 §1 records that the note does
not say so.

Three properties keep it safe:

* **Pathspec-limited.** `git add -- <paths>` and `git commit -- <paths>`, never `-A`. A tree
  that is dirty for some other reason keeps its other changes, and the commit contains only the
  instance, the event-store line and the `last_instance` edit.
* **It refuses a tree it does not own.** Creation is gated on a clean tree, the configured
  branch, and no claim in flight — the same shape as c6 and c7. The dispatcher does not add a
  file and a commit to a checkout something else is editing; that is DD-019's batch-identity
  class in the one place the design can still reach it.
* **Nothing is pushed.** A push is outward-facing; the dispatched session pushes its own work at
  the end of its task, as that project's `CLAUDE.md` already requires.

An ignored path is dropped from the commit rather than failing it, and what was dropped is
reported: a project may track its event store (the real one does) or ignore it (the test
projects do), and `git add` on an ignored path is an error that would otherwise strand a
registered task file uncommitted for a reason unrelated to it.

## Failure removes what it wrote

If the registration refuses — most likely AD-030-R11, since `dispatcher` is a gated actor and
therefore owes a design-note reference — the rendered file is unstaged and deleted, and the next
pass re-renders. A rendered file that is not in the graph is two bad things at once: a task
nothing will ever run, and a file the next pass reads as "this period is already served".

## Events

`cadence_created` carries the entry name, the period, the rule, the task id, the instance path,
the cycle name, the template, whether `last_instance` was written, any unknown placeholder in
the template, and the next due instant. **A cadence that creates nothing writes no event**, for
the same reason DN-006 decision 7 gives about empty passes: the log records assertions, and
"nothing was due" is not one. A due-but-blocked schedule is visible live through
`seldon dispatch status` and `seldon go`, which is where an operator looks.

**One defect this build found in the path it was enabling.** The not-eligible branch emitted a
`dispatch_refused` per blocked candidate, directly under a comment saying a pass with nothing
eligible writes no event. It had never run — the dispatcher shipped disabled — and every reason
reachable from there (`dirty_tree`, `above_band`, `network_undeclared`) is a **standing
condition**, re-evaluated every five minutes and unchanged until somebody edits a file. A
working tree is dirty for as long as a session is working in it, so the first enabled pass over
a two-candidate queue wrote two events and the next pass two more, for hours; and because the
event store is a tracked file, writing to it kept the tree dirty, which kept the refusal true.
The branch now writes nothing and names the reasons on stdout, where the launchd wrapper's log
carries them. The refusals that still reach the log are the ones that are occurrences rather
than states: `lease_held`, `api_key_present`, `claim_failed`.

The four `dispatch_*` types and this one are registered in `seldon/core/sync.py`'s
`_AUDIT_ONLY_EVENT_TYPES`. They were not when the dispatcher shipped, which meant a replay
logged one WARNING per dispatch — exactly the noise that set exists to keep out.

## Two defects enabling it found, which no amount of reading would have

Both are in the standing dispatcher rather than in the cadence, and both were unreachable while
`dispatch.enabled` was `false` — which is to say: shipping the mechanism switched off is what
kept them invisible, and the first minute of it being on is what showed them.

**A launchd job inherits almost no environment.** The first scheduled pass fired on time and
died on `neo4j.exceptions.AuthError`: the NEO4J_* variables a hand-run `seldon dispatch` picks
up from the shell are simply not there. The project's wrapper now falls back to that project's
existing `~/.wintermute/.env` convention. The first attempt at that fix was *also* wrong and
silently so — it deleted every quote character in the value rather than the surrounding pair,
and the password contains one, so it authenticated with a password one character short, which
is indistinguishable from a wrong password and from no password at all.

**A released lease looked like a dead holder.** `Lease.__exit__` dropped the flock and left the
body naming the holder of the finished pass, so the first brief after enabling reported a lease
held by a dead PID and told the operator to run `lease reap`. The guard was working perfectly;
the record was stale. Exit now writes the release (`holder: null`, `last_holder`,
`released_at`) and keeps the file, because the flock needs a stable inode. `reap` distinguishes
`not_held` from `no_lease_file`, and a holder that was genuinely killed still reaps.

The shared shape is worth naming: a mechanism that ships disabled has no true observations
behind it, only reasoning. Three of the defects in this build and the one before it — the
truncated dirty path, the refusal-per-pass, these two — were found by running the thing once
and reading the output.

## What `seldon go` now says

A **Dispatcher** section: enabled, the STOP file, the lease and whether its holder is alive, the
last dispatch per task with exit code and RESULT presence, **every task the dispatcher moved to
`blocked` with its log path**, and each cadence entry's period, due instant, instance and next
three firings.

It is read from the **event log and disk, never the graph**, on purpose: `seldon go` degrades
gracefully when Neo4j is down, and a brief that lost the dispatcher's state exactly when the
machine was unhealthy would be missing at the only moment it was wanted.

This is operator touchpoint 4 for the automated path — **incident notification, informational,
never an approval step**. A blocked launch is seen the next time a session opens, with the log
beside it, and nothing else notifies anyone.

## Adopting it in another project

Add a `cadence:` list to that project's `dispatch:` block and a template under its task
directory. The template is an ordinary task file carrying the three dispatch headers, a design
note reference (the dispatcher is a gated actor), and any of the five placeholders:
`{cycle_name}`, `{period}`, `{cadence_name}`, `{created_at}`, `{instance_stem}`.

`{instance_stem}` is the one to get right: the finish check looks for
`<instances_dir>/<stem>_RESULT.md`, so a template that names its RESULT any other way produces a
task the dispatcher cannot find the RESULT of — and marks `blocked` on a filename.

Substitution is a regex over exactly those five names, never `str.format`: a task file is
markdown full of JSON, Cypher and shell, and `format` would raise or mangle on every brace in
it. A `{word}` that is not one of the five is reported on the event as an unknown placeholder
rather than silently shipped.

## Tests

`tests/test_cadence.py` (63) — the calendar against a hand-checked table of first Mondays, the
month and year boundaries, naive-timestamp-as-UTC, the start boundary, the instance glob, the
closed rule vocabulary's refusals, the render's brace safety, the comment-preserving write-back,
and the pathspec-limited commit.

`tests/test_cadence_pass.py` (12, Neo4j) — the pass end to end on a frozen clock: render →
register → commit → the created task is a candidate, passes c5 by its cadence declaration, and
is launched by the same pass that created it; a second pass creates nothing; a cleared
`last_instance` creates nothing; not-due, disabled, STOP file and dirty tree each create
nothing; a period before `start_period` creates nothing; a template with no design note is
refused and its instance removed.

The clock is a seam (`_utcnow`) rather than the wall clock. A schedule whose behaviour can only
be tested during the first week of a month is a schedule that is untested for three weeks out
of four.
